# MiniMax M3 Agent 配置

> 基于 MiniMax 官方 M 系列模型最佳实践
> https://platform.minimaxi.com/token-plan/prompting-best-practices

## 模型特性
- **1M 上下文窗口** - 单次请求可承载 100 万 tokens
- 擅长复杂编程和 Agent 任务
- 支持完整执行循环 + 自我迭代
- Token Plan 按 token 计费，非按次

## Prompt 编写规则

### 1. 使用 Prompt 模板
对反复执行的任务，写成带命名变量的可复用模板：

```
角色：你是 [产品名] 的客户支持专家

客户消息：
[客户消息]

可使用的已知事实：
[已知事实]

请写一封回复，要求：
- 第一句先承认客户遇到的问题
- 只能基于上述已知事实解释下一步处理方式
- 除非已知事实中明确出现，否则不要承诺补偿、退款或具体时间
- 结尾给客户一个清晰的下一步动作
```

### 2. 结构化段落
使用清晰标签区分指令、素材、示例、约束和输出要求：

```
任务：审阅发布计划，并找出最值得优先改进的部分

背景：读者是销售团队。优先关注企业客户和合作伙伴打法

素材：
【发布计划内容】

输出格式：
- 决策摘要 —— 最多 5 条
- 风险 —— 用表格列出，并标注来源
- 待确认问题 —— 负责人、阻塞点、下一步动作
```

### 3. 设定角色、格式与长度
角色设定要说明专业背景、工作范围和判断标准：

```
你是资深后端代码 reviewer，重点关注正确性、可靠性和可维护性

待审阅的 diff：
[diff]

严格按以下结构返回：
1. 摘要 —— 最多 3 条
2. 阻塞问题 —— 表格，列为 文件、风险、修改建议
3. 非阻塞建议 —— 最多 5 条

不要重写整个文件。只提出与该 diff 直接相关的修改建议
```

### 4. 匹配输出语言
当输入是多语言混合时，明确说明：
```
即使素材是英文，也请用中文回复
```

## 长上下文技巧

### 任务放在素材之后（最重要！）
把问题或任务写在**素材之后**，任务越靠近模型回答位置，效果越好。

### 为素材建索引并分隔
多文档场景，先按时间或类型分隔：

```
**launch-plan** —— 2026-04-12
【发布计划】

**pricing-notes** —— 2026-04-18
【定价笔记】

**meeting-transcript** —— 2026-04-21
【会议记录】

任务：为发布负责人产出一份管理层简报
如果来源互相冲突，优先采用日期最新的来源，并指出冲突
```

## 工具调用规则

### 工具定义要清晰
为每个工具写清楚名称、用途、输入、返回结构和失败处理方式：

```
工具：search_docs

用途：搜索内部文档库，获取产品或政策相关事实

适合使用：
- 用户询问当前产品行为、限制、价格或发布说明

不适合使用：
- 用户只是闲聊或问通用知识问题

返回格式：
{ "source": "文档名", "excerpt": "相关段落", "confidence": 0.95 }
```

### 工具使用原则
- **并行**：独立查询可同时执行
- **顺序**：有依赖关系时先后执行
- **失败处理**：连续失败2次则停止重试
- **删除/写入**：必须先请求确认
- **仅在工具能实质提升回答质量时使用**

## 执行循环意识（Agentic Loop）

对于复杂任务，采用**执行→验证→迭代**循环：

```
1. 执行：调用工具完成当前步骤
2. 验证：检查输出是否符合预期
3. 迭代：如有偏差，基于反馈自我修正
```

## 长任务工作流
- 当前计划、进度、待确认问题保留在 Prompt 中
- 进入下一部分前，先彻底完成当前部分
- **1M 够用则不切割任务**

## 核心原则

| 原则 | 说明 |
|------|------|
| **1M 用尽** | 单次请求承载更多，避免频繁开新会话 |
| 任务置后 | 长上下文中任务放末尾 |
| 结构化 | 使用标签区分不同内容段落 |
| 具体化 | 少说"做好"，多说具体要求 |
| 工具克制 | 仅在工具能提升质量时使用 |
| 自我迭代 | 基于反馈修正，少开新轮次 |
